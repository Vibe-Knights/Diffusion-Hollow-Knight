# Отчет: фризы вывода при использовании OpenCV HighGUI

## Краткое резюме

При запуске `run_inference.py` на машине `GAME-UBUNTU` наблюдались фризы изображения: кадры некоторое время генерировались, но окно не обновлялось, после чего отображался только последний актуальный кадр. Диагностика показала, что причина не в диффузионной модели, интерполяторе или апскейлере, а в подсистеме отображения кадров через OpenCV HighGUI (`cv2.imshow` / `cv2.waitKey`) в связке с графическим стеком Linux.

Наиболее вероятная причина: конфликт или нестабильность пути вывода `OpenCV GTK3 + X11/GNOME/NVIDIA display stack`, особенно когда одна и та же NVIDIA GPU используется и для CUDA-инференса, и для вывода графического рабочего стола.

После перехода на Wayland фризы OpenCV-окна пропали, что подтверждает связь проблемы с X11/display stack. Однако глобальный ввод через `pynput` перестал работать из-за политики безопасности Wayland. Для решения ввод был перенесен на локальный backend окна, а затем заменен на `pygame`, который поддерживает корректное состояние клавиатуры и одновременные нажатия.

## Симптомы

Наблюдаемое поведение:

- изображение обновляется стабильно некоторое время;
- затем окно замирает на 2-3 секунды или дольше;
- после разморозки не проигрываются пропущенные кадры;
- сразу отображается самый новый кадр;
- при этом процесс не падает и не зависает полностью.

Важное уточнение: это не обычное падение FPS. При обычном падении FPS каждый кадр занимает больше времени. Здесь же вычислительный цикл продолжал выполняться, но окно не перерисовывалось.

## Конфигурация, на которой проявлялась проблема

Основная проблемная машина:

- GPU: NVIDIA GeForce RTX 4060 Ti;
- backend PyTorch: CUDA;
- OpenCV UI backend: `GTK3`;
- сессия: изначально `X11`;
- NVIDIA GPU использовалась и для вычислений, и для отображения;
- `nvidia-smi` показывал активный display на NVIDIA (`Disp.A On`);
- на GPU присутствовали процессы `Xorg`, `gnome-shell`, `gnome-remote-desktop-daemon`.

Машина, где проблема не проявлялась:

- ноутбук с Intel iGPU + NVIDIA RTX 3050/3050 Ti;
- вероятная схема: вывод рабочего стола идет через Intel iGPU, а CUDA-инференс идет на NVIDIA;
- за счет разделения display и compute меньше конфликтов между CUDA-нагрузкой и композитором.

## Проведенная диагностика

### 1. Проверка GPU-инференса

Было подтверждено, что `run_inference.py` запускается на CUDA:

```text
Backend: CUDA | Device: NVIDIA GeForce RTX 4060 Ti
PyTorch: 2.11.0+cu130 | CUDA: 13.0
```

Следовательно, проблема не была вызвана случайным запуском модели на CPU.

### 2. Отключение апскейлера и интерполятора

Проверялись режимы с отключенными компонентами:

```bash
python run_inference.py upscaler.enabled=false
python run_inference.py interpolator.enabled=false
```

Фризы сохранялись. Это исключило апскейлер и RIFE-интерполяцию как первопричину фризов окна.

### 3. Stall-логгер по стадиям цикла

В `run_inference.py` был добавлен логгер длительности стадий:

- input;
- generation;
- interpolation;
- upscale/render;
- display;
- pacing.

Лог показал, что при OpenCV фризы не всегда отражались как остановка Python-цикла. То есть процесс мог продолжать генерировать кадры, пока окно визуально стояло.

### 4. Heartbeat и счетчик кадров

Для отделения зависания вычислений от зависания отображения были добавлены:

- heartbeat в терминал;
- overlay-счетчик номера кадра поверх изображения.

Ключевое наблюдение:

- во время визуального фриза heartbeat продолжал идти;
- после разморозки номер кадра на изображении перескакивал вперед.

Это означает, что Python/CUDA-цикл продолжал работать, но окно не обновляло отображаемую поверхность.

### 5. Проверка Wayland

После перехода с X11 на Wayland:

- OpenCV-вывод стал работать без фризов;
- но `pynput` перестал реагировать на клавиши.

Это важный результат:

- исчезновение фризов указывает на проблему в X11/display stack;
- поломка `pynput` ожидаема, потому что Wayland запрещает обычным приложениям глобально перехватывать клавиатуру.

### 6. Проверка `ffplay`

Был добавлен backend вывода через `ffplay` pipe.

Результат:

```text
display=2835ms
display=12076ms
display=30941ms
```

То есть `ffplay` тоже мог фризить, но уже по другой причине: блокировалась запись raw frames в pipe. Поэтому `ffplay` не был выбран как финальное решение.

## Почему OpenCV может вызывать такие фризы

OpenCV HighGUI (`cv2.imshow`, `cv2.waitKey`) удобен для отладки, но это не полноценный игровой/интерактивный renderer.

Проблемные особенности:

1. `cv2.imshow` зависит от backend-а OpenCV, в данном случае GTK3.
2. На Linux отображение идет через оконную систему и compositor: X11 или Wayland.
3. На NVIDIA могут возникать задержки презентации кадра, особенно когда та же GPU одновременно:
   - считает CUDA kernels;
   - обслуживает desktop compositor;
   - выводит окно;
   - работает с GNOME Shell / remote desktop.
4. OpenCV HighGUI не дает надежного управления очередью кадров, vsync, swapchain и input state.
5. `cv2.waitKey` возвращает отдельные события клавиш, но не нормальное состояние клавиатуры, поэтому плохо подходит для одновременных нажатий.

## Почему на машине с RTX 3050 Ti проблемы нет

Разница, скорее всего, не в производительности RTX 3050 Ti и RTX 4060 Ti.

Более вероятное объяснение: различается графическая топология.

На ноутбуке с RTX 3050 Ti присутствует Intel iGPU. В такой схеме часто:

- экран подключен к iGPU;
- desktop compositor работает на iGPU;
- NVIDIA используется для CUDA-инференса;
- OpenCV-окно выводится через iGPU/display path;
- CUDA-нагрузка не конкурирует напрямую с display stack на той же NVIDIA.

На машине с RTX 4060 Ti:

- display активен на NVIDIA;
- Xorg/GNOME работают на NVIDIA;
- CUDA-инференс тоже идет на NVIDIA.

Итог: RTX 4060 Ti может быть быстрее как вычислитель, но менее стабильна в данном сценарии из-за совмещения compute и display на одной карте.

## Почему Wayland исправил фризы, но сломал `pynput`

Wayland запрещает обычным приложениям глобально читать клавиатуру. Это сделано намеренно: в X11 любое приложение могло стать keylogger-ом и читать ввод из чужих окон.

Поэтому под Wayland:

- приложение видит клавиши только в своем окне;
- глобальные key listeners вроде `pynput` часто не работают;
- правильный путь — использовать локальный ввод окна или frontend.

После этого `pynput` был удален из `run_inference.py`, а ввод был перенесен в локальный backend.

## Финальное решение

В `run_inference.py` был добавлен `pygame` backend:

```yaml
display_backend: pygame
```

Преимущества:

- не использует `cv2.imshow`;
- работает через SDL;
- поддерживает локальное состояние клавиатуры;
- корректно обрабатывает одновременные нажатия;
- совместим с Wayland-моделью безопасности;
- устраняет зависимость от глобального `pynput`.

Текущий запуск:

```bash
python run_inference.py
```

Клавиши:

- `WASD` — движение;
- `Space` — прыжок;
- `J` — лечение;
- `K` — атака;
- `Esc` — выход.

## Побочные наблюдения по интерполяции

После исправления фризов была замечена другая проблема: при включенной интерполяции субъективная производительность ухудшалась.

Причина в текущей синхронной архитектуре цикла.

При:

```yaml
interpolator:
  enabled: true
  exp: 2
```

интерполятор генерирует 3 промежуточных кадра между двумя кадрами мира, то есть всего выводятся 4 кадра на один шаг world model.

По логам:

```text
Generation ~53ms
Interpolation ~27ms
Upscale+Display ~27ms
Cycle total ~188-193ms for 4 frames
```

Это дает около 20 выводимых кадров в секунду, но сама world model обновляется только примерно 5 раз в секунду. Поэтому управление и динамика ощущаются хуже, хотя формально кадров выводится больше.

Был выбран более легкий режим:

```yaml
interpolator:
  exp: 1
```

Это дает один промежуточный кадр вместо трех и меньше снижает частоту обновления world model.

## Выводы

1. Первопричина фризов была не в модели, не в апскейлере и не в интерполяторе.
2. Фризы возникали на уровне отображения кадров через OpenCV HighGUI.
3. Связка `OpenCV GTK3 + X11 + GNOME + NVIDIA display` оказалась нестабильной для интерактивного real-time вывода.
4. Wayland устранил фризы OpenCV, но закономерно запретил глобальный ввод через `pynput`.
5. Замена `pynput` и `cv2.imshow` на локальный `pygame` backend является наиболее практичным решением для standalone-запуска.
6. Интерполяция в текущем синхронном цикле может ухудшать интерактивность, потому что снижает частоту обновления world model.

## Рекомендации

### Для текущей демонстрации

Использовать:

```yaml
display_backend: pygame
interpolator:
  exp: 1
```

Запуск:

```bash
python run_inference.py
```

### Для максимальной отзывчивости

Отключить интерполяцию:

```bash
python run_inference.py interpolator.enabled=false
```

### Для снижения нагрузки на вывод

Уменьшить размер окна:

```bash
python run_inference.py display_width=854 display_height=480
```

### Для будущей архитектуры

Если нужна одновременно высокая частота вывода и высокая частота обновления world model, текущий синхронный цикл нужно разделять:

- поток/очередь генерации world model;
- отдельный поток/цикл отображения;
- буфер последних кадров;
- возможно, интерполяция между последними доступными кадрами без блокировки генерации.

Это уже более сложная архитектура и не требуется для минимального исправления фризов.
